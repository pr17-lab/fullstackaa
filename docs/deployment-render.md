# Deployment Guide — Render + Neon

This guide covers deploying the Student Academic Tracker app (SATA) to **Render** (two Docker web services) with **Neon** as the managed Postgres database.

> **TL;DR**: Connect repo → Render detects `render.yaml` → paste secrets in dashboard → deploy. See [§3 Quick Steps](#3-quick-deploy-steps) for the 5-step version.

---

## 1. Architecture Overview

```
Browser
  │
  ▼
sata-frontend (Render, free)          sata-backend (Render, free)
┌─────────────────────────┐           ┌─────────────────────────────┐
│  nginx:1.27-alpine      │           │  python:3.11-slim + uvicorn │
│  ├── Serves /           │  HTTPS    │  ├── FastAPI REST API        │
│  └── Proxies /api/* ──────────────► │  ├── WebSocket /api/ws/*    │
│                         │           │  └── Alembic migrations      │
└─────────────────────────┘           └──────────┬──────────────────┘
                                                 │ postgresql://
                                                 ▼
                                       Neon (external, always-on)
                                       ┌────────────────────────┐
                                       │ Serverless Postgres     │
                                       │ (pooled connection)     │
                                       └────────────────────────┘
```

**Key architectural notes:**

- **No private networking** — Render's free tier does not offer private networking between services. The nginx frontend proxies `/api/*` to the backend's public `https://sata-backend.onrender.com` URL. Traffic between services goes over the public internet (HTTPS). This is an accepted tradeoff for free-tier hosting, not an oversight.
- **`BACKEND_URL` env var** — injected at nginx container start via `envsubst`. Set to the backend's public Render URL in the dashboard.
- **Neon Postgres** — provisioned externally. Supply the connection string as `DATABASE_URL`. `entrypoint.sh` runs `alembic upgrade head` before Uvicorn starts on every deploy.
- **Free tier spin-down** — both services idle-spin after **15 minutes** with no traffic. Cold starts take **50–90 seconds**. This is why the frontend has the `WsConnectionBanner` cold-start UX — it shows a "waking up" indicator during the first WebSocket connection attempt.

## 2. Prerequisites

Before deploying:

1. **Neon account + database** — already provisioned. You have:
   - A pooled connection string: `postgresql://user:pass@ep-xxx-pooler.region.aws.neon.tech/db?sslmode=require`
   - An unpooled string (for migrations): `postgresql://user:pass@ep-xxx.region.aws.neon.tech/db?sslmode=require`
   - Use the **pooled** string for `DATABASE_URL` — it handles connection multiplexing and is compatible with Render's ephemeral instances.

2. **Render account** — sign up at [render.com](https://render.com). Free tier is sufficient.

3. **GitHub repo** — ensure `render.yaml`, `backend/Dockerfile`, and `frontend/Dockerfile` are all committed and pushed.

4. **API keys** ready to paste:
   - `GROQ_API_KEY` — [console.groq.com](https://console.groq.com)
   - `GEMINI_API_KEY` — [aistudio.google.com/app/apikey](https://aistudio.google.com/app/apikey)
   - `RAPIDAPI_KEY` — [rapidapi.com](https://rapidapi.com) (optional — job listings)

## 3. Quick Deploy Steps

1. **Go to** [dashboard.render.com](https://dashboard.render.com) → **New → Blueprint Instance**

2. **Connect your GitHub repo** — authorize Render and select the repo. Render will detect `render.yaml` in the root.

3. **Fill in the `sync: false` secrets** when prompted:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | Your Neon pooled connection string |
   | `SECRET_KEY` | Auto-generated by Render (`generateValue: true`) — no action needed |
   | `CORS_ORIGINS` | `["https://sata-frontend.onrender.com"]` _(paste after noting frontend URL)_ |
   | `GROQ_API_KEY` | Your Groq API key |
   | `GEMINI_API_KEY` | Your Gemini API key |
   | `RAPIDAPI_KEY` | Your RapidAPI key (or leave blank) |
   | `BACKEND_URL` | `https://sata-backend.onrender.com` _(after backend service name is confirmed)_ |

   > **Note on ordering**: `BACKEND_URL` (frontend) and `CORS_ORIGINS` (backend) both reference the other service's URL. On first deploy, enter your expected service names (they derive from `render.yaml`'s `name` fields: `sata-backend` and `sata-frontend`). Update them after first deploy if Render appended a suffix.

4. **Click "Apply"** — Render builds and deploys both services. Build typically takes 3–5 minutes.

5. **Verify**:
   - `https://sata-backend.onrender.com/api/health` → `{"status":"healthy","database":"healthy"}`
   - `https://sata-frontend.onrender.com/` → React SPA loads, login works

## 4. Post-Deploy Configuration

### Update CORS after first deploy

Once deployed, confirm your exact service URLs. If Render appended a random suffix (e.g. `sata-backend-abc1`), update `CORS_ORIGINS` in the backend service's Environment tab in the Render dashboard:

```
["https://sata-frontend-abc1.onrender.com"]
```

### Update BACKEND_URL after first deploy

Similarly, update the frontend service's `BACKEND_URL` in the Render dashboard if the backend URL differs from expected:

```
https://sata-backend-abc1.onrender.com
```

> The nginx container must be **redeployed** after changing `BACKEND_URL` since it's injected at container startup (not dynamically at request time).

## 5. Free Tier Behaviour

| Behaviour | Detail |
|---|---|
| **Idle spin-down** | Service stops after ~15 min with no traffic |
| **Cold start time** | ~50–90 seconds for the first request |
| **Why the WsConnectionBanner exists** | The frontend's WebSocket reconnect UI shows a "Waking up server..." indicator during the first connect attempt — this is intentional UX for cold-start tolerance |
| **Database** | Neon is **always-on** (serverless — it scales to zero CPU, not connection-off) |
| **Build minutes** | Render free tier: 500 build minutes/month per service |

## 7. Alembic Migrations

Migrations run automatically on every deploy via `backend/entrypoint.sh`:

```sh
# From entrypoint.sh (simplified):
alembic upgrade head     # runs against DATABASE_URL (Neon)
uvicorn app.main:app ... # starts after migrations complete
```

To run migrations manually against Neon (e.g. for testing):

```powershell
# Windows PowerShell (from backend/ directory)
$env:DATABASE_URL="postgresql://user:pass@ep-xxx-pooler.region.aws.neon.tech/db?sslmode=require"
alembic upgrade head
```

## 8. Troubleshooting

### `database: unhealthy` on `/api/health`

- Check `DATABASE_URL` is set correctly in the Render dashboard (Backend → Environment tab)
- Verify it's the **pooled** Neon URL (contains `-pooler` in the hostname)
- Neon uses `postgresql://` — if you see `postgres://` prefix, `config.py`'s validator will reject it

### Frontend can't reach backend (`502 Bad Gateway` on `/api/*`)

- Check `BACKEND_URL` in the frontend service's Environment tab — must be the full `https://sata-backend.onrender.com` (no trailing slash)
- If `BACKEND_URL` changed, **redeploy the frontend** — envsubst bakes it in at container start, so a new deployment is required
- Check if the backend is cold-starting (wait 60–90s and retry)

### WebSocket connection stuck "Waking up..."

- Backend is cold-starting. The `WsConnectionBanner` has a 75s first-connect timeout before showing the error state
- If it exceeds 90s without connecting, check Render logs for the backend service for errors

### `alembic upgrade head` fails on deploy

- Common cause: `DATABASE_URL` not set, or Neon database is paused (Neon free tier scales to zero)
- Neon wakes on first connection — the TCP check in `entrypoint.sh` handles this correctly (it retries up to 30 times × 2s = 60s)
- Check Neon dashboard → your project → confirm the database is active

### CORS errors in browser console

- `CORS_ORIGINS` in the backend must exactly match the frontend's origin (scheme + hostname, no trailing slash)
- Example: `["https://sata-frontend.onrender.com"]` — not `https://sata-frontend.onrender.com/`

## 9. Redeployment

Render auto-deploys on every push to the repo's default branch (`render.yaml` `autoDeployTrigger` defaults to `commit`).

To trigger a manual redeploy: Render Dashboard → service → **Manual Deploy → Deploy Latest Commit**.

## 10. Local Development

Local dev is **unchanged** — Docker Compose uses a local Postgres container. Render and Neon are only for production.

```powershell
# Start everything locally
docker compose up --build
# Frontend: http://localhost:3000
# Backend:  http://localhost:8000
# API docs: http://localhost:8000/docs
```

See `docker-compose.yml` for local service configuration.
